# Storage architecture and cost model

## Problem today

Footage from Hyderabad and local Vizag shoots arrives as Google Drive links shared over WhatsApp, and editors exchange files the same way. There is no single place to find footage for a Content ID, no integrity check, no access control or download history, and no plan for 3–5 TB of new footage per month (36–60 TB per year before versions and backups).

## Target architecture

| Layer | Holds | Why |
|---|---|---|
| **Cloudflare R2 — hot** | Incoming raw footage for its first 90 days, all finals, proxies, thumbnails | S3 API, multipart/resumable uploads, **no egress fees** (editors and previews download a lot) |
| **Archive tier** (R2 Infrequent Access or Backblaze B2) | Raw footage after the hot window | Roughly half the price per TB; retrieval is slower/priced, acceptable for old raw |
| **Independent backup** (separate provider/account, object lock) | Copy of everything hot; database backups | Survives account compromise, accidental deletion, provider outage |
| **Office NAS** (Vizag) | Working copies of content currently assigned to editors | LAN-speed editing; sync agent pulls by Content ID assignment |
| **PostgreSQL** | Metadata only: asset id, Content ID, folder, object key, size, MIME, SHA-256, uploader, branch, tier, retention class, legal hold, version | Never binaries |

Folder template per Content ID: `<prefix>/<content_code>/01_RAW_FOOTAGE`, `02_EDITING_PROJECT`, `03_FIRST_CUT`, `04_REVISIONS`, `05_FINAL_EXPORT`.

### Upload flow (Milestone 6)

1. App asks the API for an upload session (Content ID, folder, file name, size, MIME, SHA-256). API checks permission, size/format rules and duplicates (same SHA-256 already stored → link instead of upload).
2. API starts an S3 multipart upload and returns presigned URLs for each part (e.g. 64 MB parts, URLs valid 1 hour). No storage credentials ever reach the device.
3. The app uploads parts directly to R2 with progress; after a dropped connection it asks which parts are confirmed and uploads only the missing ones. Mobile uploads continue in the background where the OS allows.
4. On completion the API verifies part checksums and size, finalises the object, records the asset and enqueues proxy/thumbnail generation.
5. Failures and stalled sessions notify the uploader and the producer. Every download URL is short-lived and logged.

## Capacity and cost forecast

Generated by `packages/shared/src/storage-cost.ts` (`npx tsx packages/shared/scripts/cost-table.ts`). Assumptions:

* Intake 3, 4 or 5 TB of raw footage per month.
* Finals, proxies and exports add 8% of raw volume and stay hot.
* Prices (USD per TB-month, list prices at time of writing — **verify before purchase**): hot $15 (R2 Standard), archive $6 (B2-class), backup $6.
* Excludes per-request charges (small at this scale), NAS hardware, internet bandwidth and taxes. Converting at ~₹85/USD for a rough INR view.

| 3 TB | 77.8 | 816 | 5,307 | 155.5 | 1,633 | 20,412 |

**Scenario B — 90 days hot, then archive; back up the hot tier (archive is the second copy of raw) — recommended**

**Storage is not unlimited, and costs keep rising** because footage accumulates. The single biggest lever is a **retention policy for raw footage** (for example: delete raw for routine news/social content 12 months after publishing unless flagged "keep", keep finals forever). With raw deleted after 12 months, the bill stops growing after year one (~$550/month at 4 TB/month in Scenario B). That policy is a business decision; the system will enforce it with approvals and never delete automatically without it.

### NAS sizing (get quotes)

Active working set ≈ 60 days of intake + editing projects ≈ 10–12 TB at 5 TB/month. Recommendation: a 6–8 bay NAS with RAID 6 and ~40 TB usable, 10 GbE to editing machines, UPS, and snapshots. The NAS is a working cache, **not** a backup.

### Lifecycle policies

| Class | Hot | Archive | Delete |
|---|---|---|---|
| Raw footage — client work | 90 days after final approval | until contract end + 1 year | only with approved policy |
| Raw footage — RSTAR channels | 90 days | 12 months (proposed) | proposed: after 12 months unless flagged |
| Finals / exports | forever | — | never automatic |
| Proxies / thumbnails | while asset exists | — | regenerated if lost |
| Legal hold | overrides everything | | |

### Backup and restore

* Postgres: managed point-in-time recovery (7–35 days) + nightly logical dump to the backup provider (encrypted).
* Media: hot tier replicated to the backup bucket with object lock (immutability window 30 days).
* **Restore drill quarterly**: restore the database to a scratch instance, restore a random sample of assets, verify SHA-256, record the result in `backup_checks`. An automated restore test runs in CI from Milestone 6.

## What is needed to activate (blocked on accounts/credentials)

* Cloudflare account with R2 enabled, a bucket per environment, and an API token scoped to those buckets.
* Backup provider account (separate login, separate billing owner if possible).
* Decision on raw-footage retention (the table above).
* NAS model/quote and network access for the sync agent.
